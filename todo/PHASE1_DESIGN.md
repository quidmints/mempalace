**streaming** (input = event range; output per input event) vs

### Implications

Three categories of writer need batch framing, in increasing severity:

1. **Multi-event single-shots** (`assert_triple`, sandbox lifecycle).
   The "batch" is small (3–5 events) but tearable. Need framing.

2. **Streaming lifecycles with natural batch ids** (jobs, handles, stack
   runs). Already have natural batch keys. Need to formalize them as
   batch ids and add open/close framing.

3. **True batch consumers** (migrate, canonicalizer.check_promotions,
   miner passes). N can be large. Need framing + sub-batch checkpointing
   (deferred to Phase 1.5; basic framing comes first).

### Out of scope for batch framing

- View subscribers (read-only; they advance their offset, they don't write).
- Reads in general (handled by frontier in Phase 3).
- The `BatchAborted` event itself — that's what we're adding.

## B. Idempotency-key derivation rule

The previous turn floated two candidate rules:
- streaming: `(consumer_id, input_event_offset, output_index)`
- batch: `(consumer_id, frontier_offset, run_id, output_index)`

**Decision: always use the unified form.**

```
idempotency_key = (consumer_id, batch_id, output_index)
```

Where `batch_id` is generated by the consumer at `BatchStarted` time and
*incorporates* whatever input identity the consumer wants:

- Streaming: `batch_id = f"{consumer_id}:event:{input_offset}"`
- Frontier-driven: `batch_id = f"{consumer_id}:frontier:{frontier_offset}:{run_uuid}"`
- External-trigger: `batch_id = f"{consumer_id}:trigger:{external_id}"`
  (e.g. handle_id for handle ops, match_id for sandbox ops)

The unified rule means stores need exactly one column to dedupe on, and
the recovery protocol has exactly one shape to scan for.

`output_index` is monotonic within a batch starting at 0. If a consumer
emits 15 proposals and crashes after 7, on restart the second attempt
re-emits indices 0..14 and the store skips the 7 it already saw.

`run_uuid` for frontier-driven batches handles the case where the same
frontier is processed twice (e.g. nightly recompute of signatures over
the same period). The uuid distinguishes the two runs; without it,
re-running would be incorrectly classified as a duplicate.

## C. Batch-event taxonomy (new schema events)

Three new events. All inherit from `Event`.

```python
@dataclass
class BatchStarted(Event):
    EVENT_KIND: ClassVar[str] = "batch_started"
    batch_id: str = ""
    consumer_id: str = ""
    expected_count: int = 0          # 0 if unknown
    input_summary: dict[str, Any] = field(default_factory=dict)
    # input_summary describes WHAT this batch is operating on:
    #   {"kind": "event_range", "start_offset": N, "end_offset": M}
    #   {"kind": "frontier", "offset": N, "run_uuid": "..."}
    #   {"kind": "external", "trigger_id": "..."}

@dataclass
class BatchCommitted(Event):
    EVENT_KIND: ClassVar[str] = "batch_committed"
    batch_id: str = ""
    consumer_id: str = ""
    actual_count: int = 0

@dataclass
class BatchAborted(Event):
    EVENT_KIND: ClassVar[str] = "batch_aborted"
    batch_id: str = ""
    consumer_id: str = ""
    partial_count: int = 0           # # of outputs that did land
    reason: str = ""                 # short reason code
    detail: str = ""
```

Events emitted *inside* a batch carry a new optional field
`batch_id: str = ""` on the base `Event` class. Empty string means
unbatched (legacy / single-shot ops that are atomic by nature).

## D. Recovery protocol

On consumer startup (or process restart):

1. Scan the log for `BatchStarted` events with this `consumer_id` that
   have no matching `BatchCommitted` or `BatchAborted`.

2. For each open batch:
   - Quarantine policy (default): emit `BatchAborted(reason="recovery_orphan")`.
     Outputs already written under that `batch_id` remain visible but
     are tagged. Stores expose them under a `torn_batch:` namespace via
     diagnostic API; default reads filter them out.
   - Discard policy (opt-in per consumer for cheap-to-recompute work):
     emit `BatchAborted` and have the store's recovery hook physically
     remove or invalidate prior outputs.

3. After all open batches are closed, the consumer's
   `committed_frontier_offset` is set to the highest log offset where
   everything ≤ it is fully committed (no open batches at-or-below).

4. The consumer resumes from `committed_frontier_offset + 1`. If its
   prior work was an event-range batch and the input range is still
   pending, it re-runs that range with a fresh `batch_id`. Idempotency
   keys ensure no duplicates.

### Quarantine vs discard — per-writer decision

| Writer | Policy | Why |
|---|---|---|
| `assert_triple` | discard | tiny batch; recompute trivial; partial assertion is meaningless |
| sandbox lifecycle | discard | sandbox is torn down externally on TTL; partial sandbox state is confusing |
| jobs | discard | jobs are restartable by the multiplexer |
| handles | discard | handles are short-lived; partial handle state is confusing |
| stack attestation | quarantine | attestations are forensic; we want to see what happened |
| **migrate** | **quarantine** | **migration crashes are operational events worth investigating** |
| canonicalizer promotions | quarantine | promotion decisions are interpretable; keep them for review |
| miner proposals (when they land in log) | quarantine | proposals are interpretable artifacts |

## E. Store-level deduplication

Every store that writes outputs derived from a batch needs an
idempotency-key index. Pattern:

```python
class IdempotentStore:
    def __init__(self) -> None:
        self._seen_keys: set[tuple[str, str, int]] = set()
        ...
    def add(self, record, *, idempotency_key: tuple[str, str, int] | None = None):
        if idempotency_key is not None and idempotency_key in self._seen_keys:
            return AddResult(deduplicated=True, ...)
        self._seen_keys.add(idempotency_key)
        ...
```

Stores affected: `ProposalStore`, `SignatureStore`, `Canonicalizer`
(internal candidate-cluster + canonical maps), the FOYER cache, the
`MatchedAgainstLedger` analog on the off-chain side.

## F. Open-frontier semantics

`committed_frontier_offset(consumer_id)` is the largest offset `N` such
that every batch this consumer started with first event offset ≤ N has
been closed (Committed or Aborted). Distinct from `last_processed_offset`
which can advance into open batches.

A reader requesting "consistent view as of offset M" must either:
- Wait until `committed_frontier_offset >= M` for every consumer it
  reads from; or
- Accept reads against `min(committed_frontier_offset across consumers)`.

The meet-of-frontiers concern from the previous turn lives here. We
defer the cross-consumer meet operation to Phase 3 — Phase 1 just
exposes per-consumer `committed_frontier_offset` correctly.

## G. Module-level scope of changes

Phase 1 touches:

- `mempalace/schema/events.py` — add `BatchStarted` / `BatchCommitted`
  / `BatchAborted` event classes; add `batch_id` field to base `Event`.
- `mempalace/schema/identifiers.py` — add `make_batch_id` helper.
- `mempalace/log/client.py` — new `BatchHandle` context manager that
  emits `BatchStarted` on enter, `BatchCommitted` on clean exit,
  `BatchAborted` on exception.
- `mempalace/log/recovery.py` (new) — startup scan for orphan batches.
- Every module from §A — wrap multi-event ops in `with log.batch(...)`
  context. For single-event ops, no change (the event itself is its own
  batch implicitly; we don't add framing for atomic 1-event writes).
- Tests: regression for "crash mid-batch leaves no half-formed
  assertion visible after recovery."

## H. Backwards compatibility

The new `batch_id` field on `Event` defaults to `""`. All existing
events emitted without explicit framing are treated as single-event
implicit batches. Replay of pre-Phase-1 logs Just Works — every old
event has empty `batch_id`, recovery scan finds zero orphans, frontier
advances normally.

## I. Decisions locked

1. Idempotency-key shape: `(consumer_id, batch_id, output_index)`. Unified.
2. `batch_id` is opaque from the log's perspective; consumers structure
   it however they want. Three conventional shapes documented above.
3. Default recovery policy is **quarantine** unless the writer
   explicitly opts into discard. (Reversed from my earlier instinct —
   quarantine-by-default is cheaper to debug and safe to filter.)
4. Per-event `batch_id` field defaults to empty; empty means atomic
   single-event implicit batch.
5. Phase 1 does not include sub-batch checkpointing. Migrate from
   scratch on torn migration is acceptable for now (worst case is
   re-run cost, not correctness).
6. Phase 1 does not include the cross-consumer frontier meet operator.
   That's Phase 3.

## J. What this Phase 1 does NOT yet give us

- Content-version stamps on artifacts (Phase 2).
- Cross-consumer consistent reads (Phase 3).
- Dependency tracking (Phase 4).
- Sub-batch checkpointing for cheap recovery on large batches.
- DD-level frontier coordination (Phase 5).

But after Phase 1, the answer to "did this batch commit, or was it
torn?" is a real query against the log. That's the foundation
everything else builds on.
